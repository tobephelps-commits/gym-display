Add Instagram Reels as silent visual fallback content that plays after YouTube videos are exhausted. Backend reels-fetcher service downloads .mp4 files locally from Instagram Graph API. Purpose: Ensure the video zone always has content playing — when YouTube playlist is done, Instagram Reels from the gym's own feed provide continuous visual content. If no YouTube videos are configured, Reels loop as sole content.

  <name>Task 1: Create reels-fetcher service with API endpoints</name>
  <files>services/reels-fetcher.js, server.js, config.yaml</files>
  <action>
**Update config.yaml** — add Instagram section:
```yaml
# Instagram Reels (visual fallback)
instagram:
  enabled: false
  access_token: ""
  user_id: ""
  max_reels: 20
  fetch_interval_minutes: 60
  min_display_seconds: 30
```

**Create `services/reels-fetcher.js`:**

1. **Configuration:** Read `instagram` config section via config-loader. If `enabled: false` or no access_token, log info message and operate in disabled mode (all methods return empty/safe defaults).

2. **Instagram Graph API client:**
   - `fetchReelsList()` — GET `https://graph.instagram.com/v21.0/{user_id}/media?fields=id,media_type,media_url,timestamp&access_token={token}`. Filter for `media_type === 'VIDEO'`. Return array of `{ id, media_url, timestamp }`. Handle pagination if needed (use `paging.next`). Limit to `max_reels` most recent.
   - Handle API errors gracefully: 401/403 → log token expiry warning, return empty. Network error → log and return empty.

3. **Local .mp4 download and storage:**
   - Download directory: `cache/reels/` (create if not exists)
   - `downloadReel(id, mediaUrl)` — download .mp4 to `cache/reels/{id}.mp4` using Node.js built-in fetch (Node 18+) or http/https module. Skip if file already exists and is non-empty.
   - `pruneOldReels(keepIds)` — delete .mp4 files in `cache/reels/` not in the keepIds set. Prevents unbounded storage growth.

4. **Fetch cycle:**
   - `runFetchCycle()` — fetchReelsList → download new ones → prune old ones → update internal reels list. Log summary: "Fetched X reels, downloaded Y new, pruned Z old"
   - Start interval based on `fetch_interval_minutes` config
   - Run initial fetch on construction (async, best-effort like WodScraper)

5. **Token refresh:**
   - `refreshToken()` — GET `https://graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token&access_token={token}`. On success, update internal token. Log warning if refresh fails.
   - Track token age. Attempt refresh every 30 days (well before 60-day expiry).
   - NOTE: Cannot write refreshed token back to config.yaml (would trigger hot-reload loop). Store refreshed token in memory only. Log the new token so user can update config.yaml manually if they want persistence across restarts.

6. **Public API:**
   - `getReelsList()` — returns array of `{ id, filename }` for downloaded reels
   - `getStatus()` — returns `{ enabled, reelsCount, lastFetch, tokenAge }`
   - `isEnabled()` — returns boolean

7. **Config hot-reload:** Listen for config changes, update enabled state and settings.

8. Export as singleton.

**Update server.js:**
- Require reels-fetcher
- Add `GET /api/reels` — returns `{ enabled, reels: reelsFetcher.getReelsList(), status: reelsFetcher.getStatus() }`
- Add `GET /api/reels/files/:filename` — serve .mp4 file from `cache/reels/` directory with proper Content-Type video/mp4 and Accept-Ranges for seeking. Use `res.sendFile()` with path validation (prevent directory traversal — validate filename matches `/^[a-zA-Z0-9_-]+\.mp4$/`).
- Initialize reels-fetcher in server startup (best-effort, non-fatal like WodScraper)

**Update public/app.js — add Reels playback and two-phase video zone:**

1. **Reels state variables:**
   - `reelsList` (array from API), `currentReelIndex`, `reelsEnabled`, `youtubeComplete` (boolean tracking if YouTube playlist is done)

2. **Reels player:**
   - `initReelsPlayer()` — get the `<video>` element, attach `ended` event listener that calls `playNextReel()`
   - `playNextReel()` — increment currentReelIndex (wrap around with modulo), set video.src to `/api/reels/files/{filename}`, call video.play(). Handle play() promise rejection gracefully (log error, try next reel).
   - `showReelsPlayer()` — hide yt-player div, show reels-player video element
   - `hideReelsPlayer()` — hide reels-player, pause video

3. **Two-phase video zone logic — modify `onVideoZoneActive()`:**
   - Fetch both `/api/videos` and `/api/reels` in parallel
   - Reset youtubeComplete = false, videoIndex = 0
   - **If YouTube videos exist:** Show YouTube player, start YouTube playlist (existing behavior from Plan 01)
   - **If NO YouTube videos but Reels exist:** Skip YouTube, go straight to showReelsPlayer(), start playing reels
   - **If neither:** Show "no content" fallback (existing from Plan 01)

4. **Modify `signalVideoZoneComplete()` (from Plan 01):**
   - When YouTube playlist exhausts, check if Reels are available
   - **If Reels available:** Set youtubeComplete = true, call showReelsPlayer(), playNextReel(). Do NOT advance zone yet — let Reels play.
   - **If NO Reels:** Advance zone immediately (existing behavior from Plan 01)

5. **Reels display duration and zone advancement:**
   - When in Reels mode, use `instagram.min_display_seconds` from config (fetched from `/api/config` — need to expose this). After min_display_seconds has elapsed AND current reel finishes (on `ended` event), signal zone complete via `POST /api/zones/advance`.
   - If min_display_seconds is 0 or not set, use 30 seconds as default.
   - The fallback_seconds safety timer from Plan 01 still applies as maximum.

6. **Modify `onVideoZoneInactive()`:**
   - Pause YouTube player (existing from Plan 01)
   - Also pause Reels video element if playing
   - Reset youtubeComplete = false

7. **Config update:** In `fetchConfig()`, also read `instagram.min_display_seconds` and `instagram.enabled` for frontend use. Update the `/api/config` endpoint in server.js to include the instagram enabled status and min_display_seconds (no tokens/secrets).
