<task type="auto">
  <name>Task 1: Add boost logic to zone controller</name>
  <files>services/zone-controller.js, server.js</files>
  <action>
Modify services/zone-controller.js to support class-aware rotation boosting.

**Read boost config from zones.roster in config:**
- boost_before_class_minutes (default 15) — how many minutes before class start to begin boosting
- boost_frequency (default 2) — multiplier for roster appearances during boost

**Boost mechanism:** When boost is active, dynamically modify the effective rotation order to include extra roster entries. Normal rotation: [wod, video, roster]. Boosted (freq 2): [wod, roster, video, roster]. This makes roster appear after every other zone instead of once per cycle.

**Implementation in ZoneController:**

Add to constructor:
- this._boostActive = false
- this._normalOrder (store original rotation_order)
- this._boostConfig = { beforeMinutes: 15, frequency: 2 }
- Read boost config from zones.roster section

Add **_buildBoostedOrder(normalOrder, frequency)** method:
- If frequency <= 1 or roster not in rotation, return normalOrder as-is
- Build new order: for each zone in normalOrder that isn't 'roster', add [zone, 'roster']. Remove trailing duplicate roster if last normal zone was roster.
- Example: frequency=2, normal=[wod, video, roster] → boosted=[wod, roster, video, roster]
- For frequency=3: insert roster after EVERY zone → [wod, roster, video, roster, roster] — actually just repeat the boost pattern. Keep it simple: frequency=2 means roster after each non-roster zone, frequency=3 means roster twice after each non-roster zone. But frequency=2 (the config default) is the expected use case; keep implementation simple.

Add **checkBoost(schedule)** method:
- Accept today's schedule array (from mindbody service)
- Check if any class is active or starting within boost_before_class_minutes
- If boost should be active and isn't: activate boost (swap to boosted rotation order, preserve relative position in rotation)
- If boost should be inactive and is: deactivate boost (swap back to normal order, preserve relative position)
- Log boost state changes

Add **isBoostActive()** getter — returns this._boostActive

**Wire boost checking into server.js:**

Add a periodic boost check (every 30 seconds) that calls:
```javascript
const schedule = mindbodyClient.getSchedule();
zoneController.checkBoost(schedule);
```

Place this in the server startup, after MindBody polling starts. Use setInterval. Only run if MindBody is configured.

**Update GET /api/zones/current** response to include boost info:
- Add `boostActive: zoneController.isBoostActive()` to the response

**Update config change handler** in zone controller to also re-read boost config and rebuild boosted order if boost is active.

The frontend already polls /api/config every 30 seconds and reads rotation_order + durations from it. With boost, the server's zone controller dynamically changes the effective rotation order. The frontend needs to stay in sync.

**Modify fetchConfig()** to also fetch zone state and detect boost changes:

After the existing config fetch, also fetch /api/zones/current. From the response:
- If the server's currentZone differs from local state AND the server indicates boost changed, sync local rotation to server state. This prevents the frontend and backend from drifting during boost transitions.
- Read boostActive from response. Log when boost state changes.

**Alternatively (simpler approach):** Since the backend zone controller already tracks the effective rotation order, update the /api/config endpoint to include the effective rotation order (which changes during boost). Then the frontend's existing fetchConfig() naturally picks up the boosted order.

**Preferred: Update server.js /api/config endpoint:**

In the sanitized config response, replace `zones.rotation_order` with the zone controller's current effective order:
```javascript
const zoneState = zoneController.getZoneState();
sanitized.zones.rotation_order = zoneState.rotationOrder;
sanitized.zones.boostActive = zoneController.isBoostActive();
```

This way the existing frontend fetchConfig() already reads zones.rotation_order and will pick up the boosted order. The frontend doesn't need to know about boost mechanics — it just follows whatever rotation_order the server provides.

**In app.js fetchConfig():** No changes needed for the rotation order — it already reads `zones.rotation_order` and updates the local rotationOrder variable. The boosted order will flow through automatically.

**Add boost indicator (optional but useful):** In fetchConfig(), if zones.boostActive changed from previous value, log it to console. This is purely diagnostic — no UI change needed since the roster zone already displays well.

**Ensure rotation index stays valid:** In fetchConfig(), after updating rotationOrder, if currentIndex >= rotationOrder.length, reset to 0 (this is a safety check for when boost changes the array length).
